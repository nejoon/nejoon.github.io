DATA ENGINEERING / FIELD NOTES

Everything
is a stream.

READ THE NOTE ↗

Start with an explicit event contract. Give every record a stable identifier, preserve its original timestamp, and make consumers safe to retry. A replay should be a routine operation, not an incident.

Measure freshness alongside throughput. A queue that is moving can still be falling behind. The useful question is how long it takes for a real event to become a trustworthy row.

RUBY ON RAILS / ARCHITECTURE

The case
for simple.

READ THE NOTE ↗

Keep the first boundary in the code. A small Rails application can separate responsibilities with clear models, transactions, and jobs before it needs to separate deployments.

Extract a service when you can name the operational problem it solves. Until then, one deploy and one observable request path are valuable features.

FIG. 003 / KNOW YOUR SYSTEMOBSERVE → UNDERSTAND
MAKE
IT VISIBLE.SIGNALS FROM THE OTHER SIDE OF THE DASHBOARD.

Behind every healthy dashboard is a question worth asking. Following the signal from a running system to a decision you can trust.

CLOUD INFRA / OBSERVABILITY

Signals,
not noise.

READ THE NOTE ↗

Choose a service outcome before choosing a chart. Track successful work, latency, and freshness at the boundary where a person or another system depends on you.

An alert should suggest an action. If no one can say what to investigate when a threshold is crossed, keep the signal on a dashboard while you learn its behavior.
